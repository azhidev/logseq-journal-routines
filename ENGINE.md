# Engineering entry point

The lightweight runtime replaces the former journal-projection/owner-discovery engine. Product authority is [SCOPE.md](SCOPE.md); implemented behavior and limitations are in [README.md](README.md). Continue with the Desktop validation gate in [NEXT_SESSION.md](NEXT_SESSION.md).

## Data flow

1. `register.js` owns palette commands and mounts `routines-view.js` on demand or for a graph’s pending first-run welcome. Startup/graph-switch status checks offer setup without initialization; skip uses a serialized runtime settings-only action. Pending/skipped/completed onboarding is stored in the existing graph preferences, with previously saved settings treated as already set up. Successful core Enable marks completion after period initialization; optional daily steps keep their independent error handling. Its explicit primary Setup action sequences configure → enable → optional install → guarded today application, checking graph/action generation between phases. Completion feedback distinguishes safe skips from failures; no atomic transaction or implicit lifecycle installation is claimed. The view collapses manual tools and detailed notes under More options.
2. `routines-runtime.js` captures the current graph and generation when actions are requested, serializes work and rechecks authorization around SDK operations. A graph change/Disable/unload invalidates pending work. A next-local-day timer and resume events replace polling.
3. `period-model.js` computes standalone Gregorian periods or qualifies Jalali bounds returned by `calendar-client.js`. Both calendar/kind and inclusive civil bounds participate in identity.
4. Missing definition pages use `page-metadata.js` with empty metadata to verify creation acknowledgement, page identity and fresh root state without adding bootstrap content or ownership properties; untouched native title headers remain intact. `period-snapshot.js` reads exact definition/current-period resources. Together with `routine-history.js`, it uses `page-metadata.js` to create fresh pages without SDK property objects, then parse complete metadata text through `updateBlock` on a verified first root. Native title headers are preserved; ambiguous/interrupted bootstrap pauses without adoption or repair. It uses the actual properties pre-block for mutable checkpoints. A definition fingerprint plus fresh block IDs/cursor allow verified continuation; ambiguous outcomes pause. Completed task content is never repopulated.
5. Native sidebar requests target verified summary-block UUIDs, with page fallback only for older page-only plans. Session-local automatic-open tracking respects manual closure; no sidebar-wide clear or private DOM task renderer exists.
6. `routine-history.js` creates an ordinary history page only on explicit request. Native page queries own evaluation/rendering; the plugin has no background history inventory.
7. `daily-template.js` installs an optional native daily template only through a separate graph-pinned Setup action. It uses the same text-metadata bootstrap, verifies its tree during one-shot creation, then selects `default-templates.journals` while preserving siblings and requiring approval for a different existing default. Its original-task queries use a graph-owned root containing only calendar and prefixed definition-page UUIDs. Startup/day/show and explicit settings changes can synchronize those root property lines through one verified text save; only unique unfenced lines matching the SDK metadata are eligible, with fenced examples and CRLF preserved. Ambiguous text pauses synchronization; optional errors warn separately without blocking core settings. No automatic plugin operation creates/inserts journal content, and interrupted/deleted templates are not rebuilt. Explicit reinstall can refresh only exact recognized generated heading/query presentation text, leaving custom blocks intact.
8. `daily-today.js` is a separate explicitly requested native-template application, not a daily writer. It resolves native `:today`, verifies the existing journal and an empty/one-blank-root target, pins the installed template source, persists intent before possible journal writes, invokes native insertion, and verifies copied content/structure with fresh identities. It never creates journal pages, formats date titles, modifies populated journals or retries ambiguous outcomes. `daily-presentation.js` scopes lightweight CSS to query-title markers, hiding only confirmed empty priority/pending sections and flattening query wrappers while preserving task nesting and notes.

IndexedDB stores preferences and per-resource creation markers, never task content. A graph-local initialization record is separate from the onboarding preference: it pins calendar, definition names and the two approved period identities, records intent before definition writes, and advances through definitions/periods/examples to verified only after read verification. An unfinished record blocks automatic current work across reload; explicit Enable retries the pinned attempt through existing snapshot/example verifiers, never adopting an ambiguous definition write or silently starting a different period. Starter attempt markers record verified completion only after the final preflight; completed examples are not rechecked against user edits during ordinary operation. Initialization checks are separate from navigation: auto-open respects its setting and session pane tracking, while Show/Open my routines explicitly requests panes. Write intent markers precede possible resource creation to avoid rebuilding user-deleted pages after ambiguous writes. They are local to the plugin profile and graph path; see README for backup limits.

## Host boundary

Logseq 0.10.15 page creation with a nonempty properties object can store an unserializable `cljs-bean/Bean` on the page. Avoid that API path: create with null properties and parse metadata text instead. The first-root bootstrap must become a verified native pre-block before task/query insertion. `insertBlock` acknowledgements may contain a UUID without a numeric ID; persisted identity comes from subsequent reads. A native title header may initially exist without mirrored page properties. The resulting header appears in page trees, has a separate UUID, and precedes root content. `upsertBlockProperty` must target it, not the page UUID. Mutable header state is authoritative because the page's property mirror may lag. Fixtures model this explicitly.

SDK operations and graph-switch checks are not atomic transactions. Source inspection plus fixtures improve confidence but do not replace real Desktop validation, especially metadata serialization/indexing, native sidebar behavior, history/daily-query rendering, native template insertion and default-template config persistence. The config setter discards its underlying host write promise: re-reading the in-memory setting is necessary but not proof of disk persistence. Native defaults may apply to eligible already-existing empty today/future journals, never as a plugin historical backfill.
